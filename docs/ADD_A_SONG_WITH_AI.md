# 使用 AI 添加一首歌

AI 很适合整理格式、检查一致性和生成候选时间，但不能代替对实际音频的试听。整个流程应始终以你正在使用的音频版本为准。

## 1. 先锁定音频版本

记录总时长，并试听以下锚点：

- 第一声人声
- 第一次副歌
- 间奏后的第一句
- 最后一句和尾奏

原唱、翻唱、现场、MV、AMV 和剪辑版即使歌名相同，也可能拥有不同的前奏、速度和段落。版本不匹配时，应重新制作时间轴。

可以给 AI 的要求：

```text
请先比较音频总时长、前奏、第一次副歌、间奏后和结尾五个锚点。
只有所有锚点都一致时才复用现有时间轴；不要用整体平移掩盖版本差异。
```

## 2. 建立歌曲目录

复制 `songs/不可解` 的结构并改名。修改 `song.json` 中的标题、音频、歌词和逐字文件路径。不要把音频提交到 Git。

## 3. 制作句级 SRT

句级时间决定整句何时出现。保留真实前奏、间奏和停顿，不要为了画面连续而把每句话首尾相接。

给 AI 的要求：

```text
逐句核对日文歌词与当前音频。SRT 的 start/end 必须位于真实发声边界，
保留没有演唱的空档。重复副歌也要分别试听，不能假定时间完全相同。
```

## 4. 校对歌词、读音和 ruby

至少交叉核对两个可信歌词来源，再以实际演唱确认特殊读音。歌词写法和歌手发音是两个维度：文字采用可靠歌词，ruby 按实际唱法。

规则：

- 助词按发音写：`は → wa`、`を → o`、`へ → e`。
- 每个日文字符必须有对应 ruby 单元；标点可保留空读音。
- 拗音可以合并，如 `じゃ/ja`、`きょ/kyo`。
- 促音 `っ` 的罗马音要结合后续辅音。
- 词组卡片可以包含多个字符，但卡片内部仍逐字符定位。
- 特殊读音写进歌曲自己的 `readings.json` 或 `ruby.json`，不要硬编码进 `main.py`。

给 AI 的要求：

```text
把每个词组拆成逐字符 ruby，保证日文字符序列与 SRT 完全一致。
罗马音必须位于对应字符正上方。不要把整词罗马音集中到多个字符上方。
列出所有不确定的汉字读音，等待人工对照音频确认。
```

## 5. 重建 annotation

修改 SRT、readings 或 ruby 后运行：

```powershell
py main.py --song "songs/<歌曲目录>" --reannotate
```

确认生成的 `*.annotated.json` 使用了最新数据。

## 6. 生成逐字时间初稿

准备模型输入 WAV 和 SRT，调整 `forced_align_japanese.py` 中的路径，再运行 MMS_FA 强制对齐。

句级 SRT 是硬边界。如果一句结束得太早，模型会把句尾字符挤到同一个时间点。此时应先扩大句级窗口，再重新对齐该句。

## 7. 人工精校

按以下顺序试听：

1. 句首是否与第一声同步。
2. 句尾是否覆盖完整拖音。
3. 促音、长音、弱起和连读。
4. 下一句是否过早或过晚切换。
5. 第二遍副歌和尾段是否出现累计偏移。

局部问题只改局部：

- 整句切换不准：改 SRT 和逐字文件顶层句界。
- 单个字符变色不准：只改该字符的 `start/end`。
- 读音不准：改 ruby/readings，然后重建 annotation。
- 整段漂移：重新确认音频版本和段落结构。

## 8. 让 AI 做最终审计

```text
请审计目标歌曲，不修改其他歌曲：
1. 比较 SRT、annotation、中文翻译和逐字文件的句数与日文文本；
2. 检查每个 ruby 都有非空罗马音，字符序列完全一致；
3. 检查所有时间递增、无负数、无句界外字符；
4. 找出超过一行宽度的长句，并验证两行布局不会越界；
5. 输出具体问题和文件位置，不要自动覆盖人工确认的特殊读音。
```

最后运行 `py scripts/validate_song.py`，再完整播放一次。
